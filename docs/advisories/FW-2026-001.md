# FW-2026-001: a protected change could PASS when the patch did not name its real paths

| | |
| --- | --- |
| Severity | High: a wrong PASS of every path-keyed rule, in the mode that can PASS |
| Affected | Every forge-warden commit published before 0.2.0: 0.1.0 as first published (`6cbd683`), and the GitHub `main` commits `b5de42d` and `dcce82c` |
| Fixed in | 0.2.0 (tag `v0.2.0` on GitLab and its mirrors), with one stated limit (below) |
| Published | with the 0.2.0 release |

## What went wrong

forge-warden judges the paths a patch names. Three ways of making a patch with Git produced a
well-formed patch whose paths were not the paths of the change, or that left part of the change
out. Every rule keyed on a path (`protect_paths`, `require_companion`, path-scoped waivers) then
missed the change:

1. **Non-default prefixes (ledger Q54).** With `diff.noprefix`, `diff.mnemonicPrefix`, or custom
   `diff.srcPrefix`/`diff.dstPrefix`, a change to `scripts/ci_local.sh` was read as a change to
   `ci_local.sh`. No attacker was needed: one line in a user's Git configuration was enough.
2. **A patch made from a subdirectory with `diff.relative` (ledger Q55).** The patch names paths
   relative to that directory and leaves out changes outside it.
3. **A submodule change left out (ledger Q59).** The documented by-hand `git diff` did not pin
   submodule output, so the change's own `.gitmodules` (`ignore = all`), `diff.ignoreSubmodules`
   or `diff.submodule=log` dropped a submodule change from the patch.

## Impact

Measured on the published commits with one rule, `protect_paths ["scripts/**"]` at severity fail,
where the correct verdict is FAIL (exit 7):

- `6cbd683`, its only mode: PASS (exit 0) for the prefix and the subdirectory patches.
- `b5de42d` and `dcce82c`, authority mode: PASS (exit 0) for both. Advisory mode: HOLD (exit 8)
  where FAIL was due; advisory mode cannot pass by design.
- A submodule change dropped as in item 3: the rest of the change, a protected submodule path
  included, could PASS in authority mode.

Authority mode also needs an owner-installed Git allowlist; without one it refuses (exit 3) and
never reaches the wrong PASS. Signal rules (`forbid_signal`) and score and size limits do not
depend on paths and were not affected.

## What 0.2.0 changes

- A patch is believed only if every file has a `diff --git a/PATH b/PATH` header (`b/PATH a/PATH`
  from `git diff -R` is read too). Any other header holds with `patch_unverifiable` and can never
  PASS. This closes item 1.
- `scripts/make_patch.sh BASE HEAD [REPOSITORY]` writes the patch to judge: the change from the
  merge base to head, the same bytes whatever the caller's Git configuration, environment and
  current directory: it diffs in a new repository that only borrows the object store, with
  `--no-relative`, explicit `a/` and `b/` prefixes and
  `--submodule=short --ignore-submodules=none`. The README, the runbook and the dogfood driver
  use it. This closes item 3 and, for patches made with it, item 2.
- **Stated limit (item 2):** a patch made by hand from a subdirectory with `diff.relative` is well
  formed for other paths, and nothing in its bytes shows that. 0.2.0 still judges the paths such
  a patch names. The closed fix, where forge-warden makes or checks the diff between base and head
  itself, is planned for 0.3.0.

## What to do

1. Install 0.2.0 from the repository of record:
   `cargo install --git https://gitlab.com/lukeomahoney/forge-warden --tag v0.2.0 forge-warden-cli --locked`.
2. Make every judged patch with `scripts/make_patch.sh`, never with a plain `git diff`.
3. If you judged changes with an affected commit, re-judge any PASS on a change that touched a
   protected path, with 0.2.0 and a patch from `make_patch.sh`.

## Found by

forge-warden's own team, after its 0.2.0 freeze: item 1 while reproducing a low review candidate,
item 2 while attacking the fix for item 1, item 3 by an outside-scoped code review (OpenCodeReview)
of the release range. Every reviewer was a Claude model. Details and measurements are in
`CHANGELOG.md` (0.2.0), `EVIDENCE.md` and `docs/THREAT_MODEL.md`.
