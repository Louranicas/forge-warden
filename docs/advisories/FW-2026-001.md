# FW-2026-001: a protected change could PASS when the patch did not show the real change

| | |
| --- | --- |
| Severity | High: a wrong PASS in the mode that can PASS, of every path-keyed rule (items 1 to 3) and of signal rules (item 4) |
| Affected | Every forge-warden commit published before the tag `v0.2.0`: on the GitHub repository's `main`, `6cbd683` (0.1.0), `b5de42d` (0.1.0) and `dcce82c`; and the public branch `integrate/train-13` up to and including `7f36ba2a`. **`dcce82c` already says version 0.2.0 in `Cargo.toml` but is affected by all three items. `7f36ba2a` also says 0.2.0; it already refuses item 1 and, beyond the limits 0.2.0 also has (see "Not fixed in 0.2.0"), only its documented by-hand command (items 3 and 4) is affected.** |
| Fixed in | The tag `v0.2.0` on the GitLab repository of record and its mirrors, for patches made with `scripts/make_patch.sh`. Some limits remain; see "Not fixed in 0.2.0" |
| Published | with the tag `v0.2.0` (the 0.2.0 release commit is dated 2026-11-13; the tag and this advisory came later) |

## What went wrong

forge-warden judges the patch it is given. Four ways of making a patch with Git produced a
well-formed patch whose paths were not the paths of the change, that left part of the change out,
or that hid its text. The rules that depend on what was lost then missed the change:

1. **Non-default prefixes (ledger Q54).** With `diff.noprefix`, `diff.mnemonicPrefix`, or custom
   `diff.srcPrefix`/`diff.dstPrefix`, a change to `scripts/ci_local.sh` was read as a change to
   `ci_local.sh` (measured with `diff.noprefix`). No attacker was needed: one line in a user's Git
   configuration was enough. Path-keyed rules (`protect_paths`, `require_companion`, path-scoped
   waivers) missed the change.
2. **A patch made from a subdirectory with `diff.relative` (ledger Q55).** The patch names paths
   relative to that directory and leaves out changes outside it.
3. **A submodule change left out (ledger Q59).** The documented by-hand `git diff` did not pin
   submodule output. The change itself can commit `ignore = all` to `.gitmodules`, and the patch
   then has no section for the submodule bump; `diff.ignoreSubmodules` or `diff.submodule=log` do
   the same. No setting of the user is needed: whoever writes the change chooses it.
4. **Text hidden by a committed `.gitattributes` (found 2026-11-15, before the tag).** The change
   commits `.gitattributes` with `-diff` or `binary` for the files it edits, for example
   `*.rs -diff`. The documented by-hand `git diff`, run from a work tree at the head (as CI checks
   out a pull request), reads that file and writes those files as binary sections. The ranker reads
   no lines in a binary section, so signal rules (`forbid_signal`: unsafe code, secrets, hidden
   text) see nothing. Again no setting of the user is needed.

## Impact

Measured on the published commits with one rule, `protect_paths ["scripts/**"]` at severity fail,
where the correct verdict is FAIL (exit 7). Patches were made the affected way for each item:

| Commit, mode | Item 1 (prefix) | Item 2 (`diff.relative`) | Item 3 (submodule left out) |
| --- | --- | --- | --- |
| `6cbd683`, its only mode | PASS, exit 0 | PASS, exit 0 | PASS, exit 0 |
| `b5de42d` and `dcce82c`, authority mode | PASS, exit 0 | PASS, exit 0 | PASS, exit 0 |
| `b5de42d` and `dcce82c`, advisory mode | HOLD, exit 8 | HOLD, exit 8 | HOLD, exit 8 |

Item 4 was measured on the 0.2.0 release commit (`7bd9e655`) in authority mode with the
repository's own policy: PASS, exit 0, for an added `unsafe` block, an AWS-shaped secret and a
bidirectional control character, each a rule of severity fail, when the committed
`.gitattributes` marks only the edited file types. The earlier commits document a by-hand
`git diff` that reads work-tree attributes in the same way (read from their text, not measured).

Advisory mode cannot pass by design, but a HOLD where FAIL was due is still a wrong verdict.
Authority mode needs an owner-installed Git allowlist; without one it refuses (exit 3) and never
reaches the wrong PASS. Every authority-mode row above was measured with a Git allowlist that an
agent enrolled inside a container on the owner's instruction, not one an owner installed on a host;
item 4 was measured with the owner-installed host allowlist. For items 1 to 3, signal rules
(`forbid_signal`) and score and size limits do not depend on paths and were not affected.

The measurements were made by the project's team on release builds of each commit (deep-diff-forge
0.8.2 as ranker). Their inputs and receipts are kept in the team's records, not in this
repository; `EVIDENCE.md` covers the 0.2.0 release itself.

## What 0.2.0 changes

- A patch is believed only if every file has a `diff --git a/PATH b/PATH` header (`b/PATH a/PATH`
  from `git diff -R` is read too). Any other header holds with `patch_unverifiable` and can never
  PASS. This closes item 1, except the case listed below.
- `scripts/make_patch.sh BASE HEAD [REPOSITORY]` writes the patch to judge: the change from the
  merge base to head, the same bytes whatever the caller's Git configuration, environment and
  current directory. It diffs in a new repository that only borrows the object store, with
  `--no-relative`, explicit `a/` and `b/` prefixes and
  `--submodule=short --ignore-submodules=none`, and it takes attributes from the empty tree. The
  by-hand command in the README and the runbook carries the same options, including
  `--attr-source` and `core.attributesFile=/dev/null` (Git 2.40 or later), and a test fails if the
  documents and the script drift apart. The README, the runbook and the dogfood driver use the
  script. For patches made with it, or with the documented command, items 2, 3 and 4 are closed.

## Not fixed in 0.2.0

A verdict is about the patch bytes it was given. 0.2.0 does not check that the patch is the whole
change between two commits: `--base` and `--head` are recorded as unverified claims. So a patch
made by hand can still be judged as written in these cases, and nothing in its bytes shows it:

- a custom prefix that itself begins `a/` and `b/` (for example `--src-prefix=a/x/`): a
  well-formed patch for `x/PATH`;
- a patch made from a subdirectory with `diff.relative` (item 2);
- a plain `git diff` without `--ignore-submodules=none` that leaves a submodule change out
  (item 3);
- a plain `git diff` that reads a committed `.gitattributes` from the work tree and writes text
  as binary sections (item 4); 0.2.1 is planned to hold a binary section on a path that is
  normally text, whoever made the patch;
- any other partial patch: a pathspec, or the wrong range.

The closed fix, where forge-warden makes or checks the diff between base and head itself, is
planned for 0.3.0. Until then, whoever makes the patch is inside the trust boundary: use
`scripts/make_patch.sh`.

## What to do

1. Install the tag `v0.2.0` from the repository of record:
   `cargo install --git https://gitlab.com/lukeomahoney/forge-warden --tag v0.2.0 forge-warden-cli --locked`.
   The version number alone does not tell you whether you are patched: `cargo install --list`
   shows the source with an abbreviated commit after `#`; it must be the commit the tag `v0.2.0`
   names.
2. Make every judged patch with `scripts/make_patch.sh`, never with a plain `git diff`.
3. If you judged changes with an affected commit, re-judge any PASS on a change that touched a
   protected path, with 0.2.0 and a patch from `make_patch.sh`.
